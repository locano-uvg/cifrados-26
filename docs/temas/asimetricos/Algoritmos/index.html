Niveles de Seguridad (bits)

Un "bit de seguridad" representa cuánto esfuerzo computacional se necesita para romper el sistema (2^n operaciones).

Seg. (bits) RSA / DH clásico ECC Simétrico Estado
80 bits RSA-1024 160 bits 2-TDEA Obsoleto
112 bits RSA-2048 224 bits 3-TDEA Mínimo aceptable
128 bits RSA-3072 256 bits AES-128 Recomendado
192 bits RSA-7680 384 bits AES-192 Alta seguridad
256 bits RSA-15360 521 bits AES-256 Muy larga duración

Fuente: NIST SP 800-57 Part 1 Rev. 5

Conclusión de la tabla

  • ECC-256 ≈ RSA-3072 en seguridad, pero ECC es mucho más eficiente
  • RSA-1024 es inseguro — factorizado en 2010
  • Para nuevos sistemas: mínimo 128 bits de seguridad
  • Para datos que deben durar > 10 años: considerar 192 bits

Diffie-Hellman (DH)

Primer protocolo de intercambio de claves sobre canal inseguro (1976). Permite establecer un secreto compartido sin haberlo compartido antes.

Principio: gab mod p es el secreto compartido, calculado independientemente por ambas partes.

  • Alice envía: A = ga mod p
  • Bob envía: B = gb mod p
  • Secreto: S = Ba = Ab = gab mod p

DH Estático vs DHE (Efímero)

  • DH Estático: Siempre las mismas claves — sin Perfect Forward Secrecy (PFS). Comprometer la clave privada expone todas las sesiones pasadas
  • DHE: Nuevas claves efímeras por sesión — con PFS. Comprometer la clave privada de hoy no afecta sesiones de ayer

TLS 1.3 eliminó completamente el DH estático. Solo permite DHE o ECDHE.

Ataque Logjam (2015)

  • Grupos DH de 512 bits podían romperse en tiempo real por un atacante activo
  • Grupos de 768 y 1024 bits eran vulnerables con precomputación
  • Afectó TLS, SSH, IKE/IPsec — millones de servidores
  • Los atacantes podían degradar conexiones a grupos débiles (downgrade attack)

Solución: Usar grupos DH de 2048+ bits o preferir ECDHE (X25519)

Problemas de DH clásico

  • Sin autenticación integrada — vulnerable a MITM sin autenticación adicional
  • Grupos débiles o mal configurados son explotables
  • Parámetros globales compartidos reducen seguridad por precomputación

Por eso en la práctica se usa ECDHE con curvas modernas (X25519) — más rápido, más seguro, sin grupos compartidos débiles.

ElGamal y DSA

Sistema de cifrado asimétrico y firmas digitales (1985) basado en el problema del logaritmo discreto. DSA es la variante de firma estandarizada por NIST.

  • Seguro bajo la hipótesis del logaritmo discreto
  • Probabilístico: el mismo mensaje produce cifrados diferentes
  • El texto cifrado es el doble del tamaño del mensaje
  • Más lento que RSA y ECC en la práctica
  • DSA vulnerable si se reutiliza o predice el nonce k

El Problema del Nonce en DSA / ECDSA

DSA/ECDSA usa un número aleatorio k para cada firma. Si k se reutiliza en dos firmas (r₁, s₁) y (r₂, s₂) del mismo mensaje hash: 

# k es el mismo en dos firmas => r1 == r2
# s1 = (h1 + x*r) / k  mod q
# s2 = (h2 + x*r) / k  mod q
# k = (h1 - h2) / (s1 - s2)  mod q  [recuperable]
# x = (s1*k - h1) / r  mod q  [clave privada expuesta]

Caso real: Sony PlayStation 3 (2010) — usaban k constante en todas las firmas. Todos los binarios del sistema firmados con la misma k. Clave privada de Sony expuesta completamente.

Solución: Nonce Determinístico (RFC 6979)

En lugar de k aleatorio (que puede fallar), usar k derivado determinísticamente del mensaje + clave privada: 

from cryptography.hazmat.primitives.asymmetric import ec
from cryptography.hazmat.primitives import hashes

# Ed25519 usa nonce determinístico por diseño — inmune a este ataque
private_key = ec.generate_private_key(ec.SECP256K1())
signature = private_key.sign(b"mensaje", ec.ECDSA(hashes.SHA256()))
# Python cryptography usa RFC 6979 automáticamente para ECDSA

Preferir Ed25519 que es inmune a este problema por diseño.

ECDH — Diffie-Hellman en Curvas Elípticas

Versión de DH sobre curvas elípticas. La operación análoga a la exponenciación modular es la multiplicación escalar de puntos.

  • Alice genera k_A, calcula Q_A = k_A × G (G = punto base de la curva)
  • Bob genera k_B, calcula Q_B = k_B × G
  • Intercambian Q_A y Q_B sobre el canal inseguro
  • Secreto compartido: S = k_A × Q_B = k_B × Q_A = k_A × k_B × G

La seguridad se basa en el ECDLP (Elliptic Curve Discrete Log Problem): dado G y Q = k×G, encontrar k es computacionalmente inviable.

ECDH en Código (X25519)

from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey

# Alice genera su par de claves
alice_private = X25519PrivateKey.generate()
alice_public = alice_private.public_key()

# Bob genera su par de claves
bob_private = X25519PrivateKey.generate()
bob_public = bob_private.public_key()

# Intercambian claves públicas (canal inseguro)
# Calculan el secreto compartido
alice_shared = alice_private.exchange(bob_public)
bob_shared = bob_private.exchange(alice_public)

assert alice_shared == bob_shared  # Mismo secreto sin haberlo compartido
print("Secreto compartido:", alice_shared.hex())

X25519 es ECDH sobre Curve25519 — el más recomendado actualmente.

Ventajas de ECDH sobre DH clásico

Aspecto DH Clásico ECDH (X25519)

Tamaño de mensaje Grande Compacto
Ataques de subgrupo Posibles Mitigados (cofactor)

ECC — Curvas Elípticas

Ofrece mayor seguridad con claves más cortas y mejor rendimiento.

  • Claves más cortas: ECC-256 ≈ RSA-3072
  • Más eficiente: ideal para IoT, móviles, embedded
  • TLS 1.3 lo prefiere sobre RSA para intercambio de claves
  • Matemáticamente más complejo de implementar correctamente
  • Algunas curvas antiguas tienen parámetros cuestionables (Dual_EC_DRBG — backdoor NSA confirmado)

Post-Quantum Cryptography (PQC)

La Amenaza Cuántica

  • El algoritmo de Shor (1994) puede romper RSA y ECC en tiempo polinomial con una QC suficientemente grande
  • RSA-2048 requeriría ~4,000 qubits lógicos para ser roto. Actualmente (2026) las QC más avanzadas tienen cientos de qubits con alta tasa de error — aún no criptoanalíticamente relevantes
  • "Harvest now, decrypt later": adversarios ya capturan tráfico cifrado hoy para descifrarlo cuando la QC esté disponible. Los datos confidenciales de hoy ya están en riesgo

Estándares NIST PQC (Agosto 2024)

Estándar Algoritmo base Tipo Problema duro
FIPS 203 ML-KEM (Kyber) KEM / Intercambio de claves Module-LWE (retículos)
FIPS 204 ML-DSA (Dilithium) Firmas digitales Module-LWE + SIS (retículos)
FIPS 205 SLH-DSA (SPHINCS+) Firmas digitales Seguridad solo en hash

FALCON (FN-DSA, FIPS 206) también fue estandarizado — firmas más compactas

Criptografía Híbrida Post-Cuántica

Estrategia recomendada: combinar algoritmo clásico + PQC en paralelo. Si uno falla, el otro protege.

  • X25519 + ML-KEM-768: ya implementado en Chrome, Firefox, Cloudflare desde 2023-2024 para TLS
  • Si la QC rompe ML-KEM → X25519 mantiene seguridad clásica
  • Si un ataque clásico surge → ML-KEM mantiene seguridad cuántica
  • NIST recomienda migrar sistemas críticos antes de 2030

¿Qué Algoritmo Usar?

  • TLS/HTTPS moderno: ECDHE (X25519) + AESGCM. Usar TLS 1.3 — obligatorio en nuevos sistemas
  • Firmas en Blockchain: secp256k1 con ECDSA (Bitcoin/Ethereum); Ed25519 para cadenas modernas (Solana, Cardano)
  • SSH: Ed25519 — más seguro y rápido que RSA-4096. Generar con ssh-keygen -t ed25519
  • IoT / Embedded: ECC (Ed25519, X25519) por restricciones de recursos
  • Correo seguro (GPG): ECC ed25519 + cv25519 sobre RSA legacy
  • Largo plazo (> 2030): ML-KEM (FIPS 203) + ML-DSA (FIPS 204)

Regla Fundamental

"Don't roll your own crypto."

Los errores de implementación son la causa más común de vulnerabilidades criptográficas — no las fallas matemáticas del algoritmo.

  • Python: cryptography, PyNaCl (libsodium)
  • JavaScript/Node: WebCrypto API, Noble Cryptography
  • Go: golang.org/x/crypto
  • C/C++: libsodium, OpenSSL 3.x
