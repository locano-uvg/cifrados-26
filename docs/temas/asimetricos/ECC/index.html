Criptografía de Curvas Elípticas

(ECC — Elliptic Curve Cryptography)

¿Qué es ECC?

ECC es un sistema criptográfico basado en las matemáticas de curvas elípticas sobre campos finitos.

  • Proporciona el mismo nivel de seguridad que RSA con claves mucho más cortas
  • Más eficiente en términos de almacenamiento, cómputo y ancho de banda
  • Soporta: cifrado (ECIES), firmas (ECDSA, EdDSA) e intercambio de claves (ECDH)
  • Propuesto independientemente por Neal Koblitz y Victor Miller en 1985

Fundamento Matemático

¿Qué es una Curva Elíptica?

Una curva elíptica es el conjunto de puntos (x, y) que satisfacen:

y² = x³ + ax + b (sobre un campo)

Con la condición que el discriminante 4a³ + 27b² ≠ 0 (sin cúspides ni self-intersections)

  • En criptografía, se trabaja sobre campos finitos Fp (aritmética modular): y² ≡ x³ + ax + b (mod p)
  • Los puntos forman un grupo abeliano bajo una operación de suma definida geométricamente

Operaciones en la Curva

  • Suma de puntos (P + Q): Se traza una línea entre P y Q, se busca la intersección con la curva y se refleja sobre el eje x
  • Doblado de punto (2P = P + P): Se usa la tangente en P
  • Multiplicación escalar (k × P): Suma repetida k veces. Ej: 5P = P + P + P + P + P. Se calcula eficientemente con "double-and-add"
  • Punto en el infinito (O): Elemento neutro del grupo. P + O = P

El Problema del Logaritmo Discreto en Curvas Elípticas (ECDLP)

Dado un punto base G y un punto público Q = k × G, encontrar el escalar k es computacionalmente inviable.

  • Fácil: k × G (multiplicación escalar, eficiente con double-and-add)
  • Difícil: dado G y Q, encontrar k (ECDLP)
  • El mejor algoritmo conocido para ECDLP es Baby-step Giant-step: O(√p) — mucho más difícil que factorización para el mismo tamaño de clave

Curva secp256k1 — Bitcoin

La curva que usa Bitcoin: y² = x³ + 7 (mod p)

from cryptography.hazmat.primitives.asymmetric import ec

# La curva secp256k1 de Bitcoin
# a=0, b=7, campo primo p = 2^256 - 2^32 - 2^9 - 2^8 - 2^7 - 2^6 - 2^4 - 1

# Generar clave privada (escalar k aleatorio)
private_key = ec.generate_private_key(ec.SECP256K1())
public_key = private_key.public_key()

# La clave pública es el punto Q = k * G en la curva
print("Clave privada:", private_key.private_numbers().private_value)
pub_numbers = public_key.public_numbers()
print("Clave pública (x,y):", pub_numbers.x, pub_numbers.y)

ECDH — Intercambio de Claves

Diffie-Hellman sobre curvas elípticas. El secreto compartido es el resultado de la multiplicación cruzada de claves privadas y públicas.

  • Alice: clave privada a → pública Q_A = a × G
  • Bob: clave privada b → pública Q_B = b × G
  • Alice calcula: S = a × Q_B = a × b × G
  • Bob calcula: S = b × Q_A = b × a × G
  • Ambos obtienen el mismo punto S — sin haberlo compartido. El atacante solo ve G, Q_A y Q_B — no puede calcular S (ECDLP)

ECDH con X25519 (Recomendado)

from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey
from cryptography.hazmat.primitives.serialization import (
    Encoding, PublicFormat
)

# Alice genera su par
alice_private = X25519PrivateKey.generate()
alice_public_bytes = alice_private.public_key().public_bytes(
    Encoding.Raw, PublicFormat.Raw
)

# Bob genera su par
bob_private = X25519PrivateKey.generate()
bob_public_bytes = bob_private.public_key().public_bytes(
    Encoding.Raw, PublicFormat.Raw
)

# Intercambian claves públicas (canal inseguro)
# Calculan el secreto compartido
from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PublicKey
alice_shared = alice_private.exchange(
    X25519PublicKey.from_public_bytes(bob_public_bytes)
)
bob_shared = bob_private.exchange(
    X25519PublicKey.from_public_bytes(alice_public_bytes)
)

assert alice_shared == bob_shared
print("Secreto compartido:", alice_shared.hex())

Derivación de Clave desde ECDH

El secreto compartido S NO se usa directamente como clave — puede tener bias o estructura. Se pasa por una función de derivación (KDF): 

import hashlib, hmac
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes

# Derivar clave AES-256 del secreto compartido ECDH
shared_secret = alice_shared

hkdf = HKDF(
    algorithm=hashes.SHA256(),
    length=32,  # AES-256
    salt=None,
    info=b"handshake data v1"
)
clave_aes = hkdf.derive(shared_secret)
print("Clave AES-256:", clave_aes.hex())

ECDSA — Firmas Digitales

¿Cómo Funciona ECDSA?

Firma (usando clave privada d):

  1. Calcular hash del mensaje: e = H(mensaje)
  2. Generar nonce aleatorio k (crítico: debe ser único por firma)
  3. Calcular punto R = k × G → tomar r = R.x mod n
  4. Calcular s = k⁻¹(e + r × d) mod n
  5. Firma = (r, s)

Verificación (usando clave pública Q):

  1. u₁ = e × s⁻¹ mod n, u₂ = r × s⁻¹ mod n
  2. Punto V = u₁ × G + u₂ × Q
  3. Válido si V.x mod n == r

ECDSA en Código (Python)

from cryptography.hazmat.primitives.asymmetric import ec
from cryptography.hazmat.primitives import hashes

# Generar par de claves (P-256 para interoperabilidad)
private_key = ec.generate_private_key(ec.SECP256R1())
public_key = private_key.public_key()

# Firmar (la librería aplica SHA-256 + ECDSA internamente)
mensaje = b"Transaccion: Alice -> Bob: 0.5 BTC"
firma = private_key.sign(mensaje, ec.ECDSA(hashes.SHA256()))
print("Firma ECDSA:", firma.hex()[:32], "... (DER format)")

# Verificar
try:
    public_key.verify(firma, mensaje, ec.ECDSA(hashes.SHA256()))
    print("Firma VÁLIDA")
except Exception as e:
    print("Firma INVÁLIDA:", e)

La librería `cryptography` usa RFC 6979 (nonce determinístico) automáticamente — evita el error de Sony PS3.

El Fallo Catastrófico de Sony PS3 (2010)

  • Sony firmaba todos los binarios de PS3 con ECDSA usando el mismo valor k en cada firma
  • Matemáticamente: si k es idéntico en dos firmas (r₁=r₂=r): k = (h₁ - h₂) × (s₁ - s₂)⁻¹ mod n
  • Una vez conocido k: d = (s×k - h) × r⁻¹ mod n — clave privada de Sony completamente expuesta
  • El grupo fail0verflow y George Hotz publicaron la clave — cualquiera podía firmar software "oficial" para la consola

EdDSA — Ed25519

¿Por qué Ed25519 sobre ECDSA?

EdDSA (Edwards-curve Digital Signature Algorithm) fue diseñado para eliminar las vulnerabilidades comunes de ECDSA:

  • Nonce determinístico: k = H(clave_privada || mensaje). No puede reutilizarse. Inmune al ataque Sony PS3
  • Tiempo constante: Resistente a timing attacks por diseño
  • Sin parámetros cuestionables: Curve25519 fue diseñada con criterios de seguridad transparentes por D.J. Bernstein
  • Más rápido: Verificación ~2x más rápida que ECDSA-P256

Ed25519 en Código (Python)

from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PrivateKey
from cryptography.hazmat.primitives.serialization import (
    Encoding, PublicFormat, PrivateFormat, BestAvailableEncryption
)

# Generar par de claves
private_key = Ed25519PrivateKey.generate()
public_key = private_key.public_key()

# Serializar clave pública (32 bytes compactos)
pub_bytes = public_key.public_bytes(Encoding.Raw, PublicFormat.Raw)
print("Clave pública Ed25519:", pub_bytes.hex())

# Firmar — nonce determinístico, tiempo constante, 64 bytes
mensaje = b"Contrato digital autenticado"
firma = private_key.sign(mensaje)
print("Firma Ed25519 (64 bytes):", firma.hex())

# Verificar
try:
    public_key.verify(firma, mensaje)
    print("Firma VÁLIDA")
except Exception:
    print("Firma INVÁLIDA")

Curvas Seguras vs Inseguras

Criterios de una Curva Segura (SafeCurves)

safecurves.cr.yp.to — proyecto de D.J. Bernstein que evalúa curvas según criterios de seguridad e implementabilidad:

  • CM discriminante grande: resistencia a ataques de subgrupo
  • Twist security: resistencia a ataques en la curva torcida
  • Completitud: suma de puntos siempre definida (evita casos especiales que causan bugs)
  • Tiempo constante: implementable sin branches secretos

Curvas Recomendadas

Curva Uso SafeCurves Notas
Curve25519 X25519 (ECDH) Sí Recomendado para TLS, SSH
Ed25519 EdDSA (firmas) Sí Recomendado para firmas
P-256 (NIST) ECDSA, ECDH Parcial Ampliamente soportado
secp256k1 Bitcoin/Ethereum Parcial Solo para compatibilidad
Dual_EC_DRBG PRNG (NSA) Backdoor NSA NUNCA usar

Dual_EC_DRBG — El Backdoor de la NSA (2013)

  • Generador de números pseudoaleatorios basado en curvas elípticas, estandarizado por NIST en 2006
  • Revelaciones de Snowden (2013) confirmaron que la NSA pagó a RSA Security 10 millones USD para hacer este PRNG el predeterminado en su toolkit
  • Si la NSA conoce la relación entre los dos puntos Q y P usados, puede predecir todos los valores aleatorios generados — rompiendo toda la criptografía que depende de él
  • Afectó: Juniper Networks, RSA BSAFE, OpenSSL hasta 2014

Aplicaciones de ECC

  • TLS 1.3 / HTTPS: ECDHE con X25519 o P-256 para intercambio de claves. ECDSA o EdDSA para certificados
  • Blockchain: secp256k1 + ECDSA (Bitcoin, Ethereum); Ed25519 (Solana, Cardano, Monero)
  • SSH: Ed25519 para autenticación de usuarios y servidores
  • Signal / WhatsApp / iMessage: X25519 + Ed25519 en el protocolo de mensajería
  • Dispositivos IoT: ECC por restricciones de CPU y memoria
  • Passport y DNI electrónico: ECDSA sobre curvas NIST para firmas y autenticación

Errores Comunes en ECC

  • Reutilizar nonce k en ECDSA: Expone la clave privada completamente — el error de Sony PS3. Usar Ed25519 o asegurarse de usar RFC 6979
  • Usar curvas con parámetros cuestionables: Evitar curvas NIST si la privacidad es crítica y se desconfía del origen de los parámetros. Preferir Curve25519
  • No validar el punto público recibido: Un punto en la curva torcida puede filtrar bits de la clave privada. Usar curvas con twist security (Curve25519)
  • Implementar ECC desde cero: Los casos especiales (punto en el infinito, cofactor) son trampas. Usar libsodium, cryptography (Python), Web Crypto API
  • Confundir ECDH y ECDSA: Son operaciones distintas. La clave de un par ECDH no debe usarse para firmar — clave única por propósito
  • No derivar la clave del secreto ECDH: El punto S = k × Q no debe usarse directamente como clave AES. Siempre pasar por HKDF u otra KDF
  • Ignorar small subgroup attacks: Con algunas curvas, claves públicas mal formadas pueden forzar al otro extremo a operar en un subgrupo pequeño. Validar siempre el orden del punto recibido

Conclusión

ECC es la mejor alternativa a RSA para aplicaciones modernas por su alta seguridad, eficiencia y claves compactas.

  • Para intercambio de claves: X25519 (ECDH)
  • Para firmas digitales: Ed25519 (EdDSA)
  • Para compatibilidad amplia: P-256 (ECDSA)
  • Para blockchain legacy: secp256k1 (ECDSA)

Migrar de RSA a Ed25519/X25519 mejora seguridad, rendimiento y reduce superficie de ataque sin sacrificar compatibilidad.
