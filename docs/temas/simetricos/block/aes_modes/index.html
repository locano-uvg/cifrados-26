El truco del formato PPM

Las imágenes PPM almacenan píxeles como bytes RGB sin comprimir. Si ciframos solo el cuerpo pero conservamos el encabezado original, cualquier visor de imágenes puede abrir el resultado. Lo que se vea —o no se vea— revela la calidad del cifrado.

Estructura de un archivo PPM
1 P6 ← Formato binario
2 265 314 ← Ancho × Alto
3 255 ← Valor máximo
— FF 4A 1C 80 22 ... (píxeles RGB)
◀ Conservamos  |  Ciframos ▶
⬡ Encabezado → intacto ⬡ Cuerpo → cifrado
¿Por qué es un buen banco de pruebas? Una imagen real tiene zonas homogéneas (fondo uniforme, colores sólidos). Esos bloques de píxeles repetidos son exactamente lo que un modo débil como ECB no puede esconder.
Un cifrado seguro debe verse como ruido Si después del cifrado aún se puede identificar la forma del objeto, el modo falló en ocultar el patrón estadístico del mensaje original.

La lección fundamental ECB usa exactamente el mismo algoritmo AES que CBC y CTR. La clave es idéntica. La diferencia es cómo se encadenan los bloques. Un modo de operación deficiente convierte un cifrador fuerte en uno inseguro.
Modo de cifrado

ECB — Electronic Codebook

Cada bloque de 16 bytes se cifra de manera completamente independiente. No hay memoria del bloque anterior. Esto lo hace el modo más simple de entender, y también el más peligroso.

Paso 0 / 4

¿Por qué ECB falla?

ECB aplica AES directamente a cada bloque de 16 bytes de manera independiente. Significa que dos bloques con el mismo contenido producen exactamente el mismo bloque cifrado.

En una imagen, los píxeles del fondo son uniformes: miles de bloques de 16 bytes idénticos. Cuando se cifran con ECB todos producen el mismo ciphertext, preservando la estructura visual.

ECB no es semánticamente seguro Un atacante puede distinguir si dos bloques de la imagen tienen el mismo contenido simplemente comparando el ciphertext, sin conocer la clave.

Fórmula ECB

Ci = AESK(Pi)
Sin estado. Sin dependencias entre bloques.

Modo de cifrado

CBC — Cipher Block Chaining

Antes de cifrar cada bloque, se hace un XOR con el bloque cifrado anterior. El primer bloque usa un Vector de Inicialización (IV) aleatorio. Esto rompe cualquier patrón estadístico.

Paso 0 / 5

¿Por qué CBC funciona mejor?

El XOR con el bloque anterior introduce dependencia de contexto. Aunque dos bloques de plaintext sean idénticos, su posición en la cadena les da un ciphertext diferente.

El IV garantiza unicidad El Vector de Inicialización debe ser aleatorio y único por mensaje. Así dos cifrados del mismo plaintext con la misma clave producen ciphertexts completamente diferentes.
Limitaciones de CBC El procesamiento es secuencial: no se puede paralelizar el cifrado porque cada bloque depende del anterior. Además es susceptible a ataques de padding oracle si no se implementa con cuidado.

Fórmula CBC

Ci = AESK(Pi ⊕ Ci-1)
C0 = IV (aleatorio)
Modo de cifrado

CTR — Counter Mode

CTR convierte AES en un cifrado de flujo. No cifra el plaintext directamente; cifra un contador incrementado secuencialmente y luego hace XOR con el plaintext. No necesita padding.

Diagrama interactivo CTR — Presiona "Siguiente paso"
Paso 0 / 4

CTR: lo mejor de dos mundos

CTR genera un keystream cifrando valores de contador sucesivos. El plaintext nunca entra directamente al núcleo AES — solo el contador lo hace. El XOR final convierte AES en un cifrado de flujo.

Paralelizable A diferencia de CBC, todos los bloques del keystream se pueden generar de forma independiente y simultánea. Ideal para hardware con múltiples cores.
Sin padding Como el keystream se genera con la misma longitud que el mensaje, no se necesita completar el último bloque. El ciphertext tiene exactamente el mismo tamaño que el plaintext.
Nonce único es crítico Si se reutiliza el mismo nonce+clave con dos mensajes distintos, el XOR de ambos ciphertexts revela el XOR de los plaintexts — ataque devastador.

Fórmula CTR

Ci = Pi ⊕ AESK(Nonce ∥ i)
AES solo cifra el contador. El plaintext nunca entra al bloque AES.
Implementación

El código fuente

Tres funciones, tres comportamientos radicalmente distintos. La biblioteca pycryptodome maneja los detalles de bajo nivel de AES.

split_head_body_img.py 
def split_head_body(image_path: str) -> tuple[bytes, bytes]:
    with open(image_path, "rb") as f:
        data = f.read()
    # PPM tiene un header de 3 líneas: formato, dimensiones, max color
    header_end = 0
    for _ in range(3):
        header_end = data.index(b"\n", header_end) + 1
    return data[:header_end], data[header_end:]
Concepto clave Al separar el encabezado de los datos de píxeles, podemos cifrar solo el cuerpo y luego reconstruir un archivo PPM válido que cualquier visualizador puede abrir. El truco está en que el encabezado PPM define las dimensiones — sin él, los píxeles no tienen estructura.
aes_encrypt_modes.py 
from Crypto.Cipher import AES
from Crypto.Util.Padding import pad

def encrypt_ecb(body: bytes, key: bytes) -> bytes:
    # ECB: cada bloque de 16 bytes se encripta de forma independiente
    # bloques de píxeles idénticos → ciphertext idéntico → patrones visibles
    cipher = AES.new(key, AES.MODE_ECB)
    encrypted = cipher.encrypt(pad(body, AES.block_size))
    return encrypted[:len(body)]   # truncar al tamaño original


def encrypt_cbc(body: bytes, key: bytes) -> bytes:
    # CBC: cada bloque se XOR con el ciphertext anterior antes de encriptar
    # IV aleatorio → los patrones desaparecen, resultado parece ruido
    cipher = AES.new(key, AES.MODE_CBC)   # IV aleatorio por defecto
    encrypted = cipher.encrypt(pad(body, AES.block_size))
    return encrypted[:len(body)]


def encrypt_ctr(body: bytes, key: bytes) -> bytes:
    # CTR: convierte AES en cifrado de flujo, encripta un contador y XOR con plaintext
    # no necesita padding, opera byte a byte → tamaño de salida igual al de entrada
    cipher = AES.new(key, AES.MODE_CTR, nonce=b"")   # nonce vacío → counter 128 bits
    return cipher.encrypt(body)
¿Por qué se trunca el resultado en ECB y CBC? AES opera sobre bloques de 16 bytes exactos. El padding completa el último bloque si el cuerpo de la imagen no es múltiplo de 16. Al truncar con [:len(body)], devolvemos exactamente los mismos bytes que entraron — fundamental para que el PPM tenga el tamaño correcto.
encriptar_AES.py 
from Crypto.Random import get_random_bytes
from split_head_body_img import split_head_body
from aes_encrypt_modes import encrypt_ecb, encrypt_cbc, encrypt_ctr
import os

def write_ppm(header: bytes, body: bytes, output_path: str) -> None:
    with open(output_path, "wb") as f:
        f.write(header + body)

root = os.path.dirname(os.path.abspath(__file__))
input_path = os.path.join(root, "tux.ppm")

key = get_random_bytes(16)   # Clave aleatoria de 128 bits (AES-128)
print(f"Clave AES (hex): {key.hex()}\n")

header, body = split_head_body(input_path)
print(f"Header: {len(header)} bytes")
print(f"Body  : {len(body)} bytes  ({len(body) // 3} píxeles)\n")

# Cifrar con cada modo usando la misma clave
encrypted_body_cbc = encrypt_cbc(body, key)
encrypted_body_ecb = encrypt_ecb(body, key)
encrypted_body_ctr = encrypt_ctr(body, key)

# Escribir los archivos PPM con el header original + body cifrado
write_ppm(header, encrypted_body_ecb, "tux_encrypted_ecb.ppm")
write_ppm(header, encrypted_body_cbc, "tux_encrypted_cbc.ppm")
write_ppm(header, encrypted_body_ctr, "tux_encrypted_ctr.ppm")
Punto importante sobre la clave La clave se genera aleatoriamente con get_random_bytes(16) cada vez que se ejecuta el script. Los tres modos comparten la misma clave para que la única variable sea el modo de operación.
Conclusiones

Comparativa de modos

El algoritmo AES subyacente es el mismo en los tres casos. Lo que los diferencia —y lo que determina su seguridad en la práctica— es el modo de operación.

Característica ECB CBC CTR
Oculta patrones estadísticos ✗ NO ✓ SÍ ✓ SÍ
Necesita IV / Nonce ✗ No ✓ IV aleatorio ✓ Nonce único
Necesita padding ⚠ Sí (PKCS7) ⚠ Sí (PKCS7) ✓ No
Procesamiento paralelo ✓ Sí ✗ Solo descifrado ✓ Completo
Acceso aleatorio ✓ Sí ✗ No ✓ Sí
Propagación de errores Solo en el bloque afectado 2 bloques (actual + siguiente) Solo en el byte afectado
Uso recomendado ✗ Nunca ⚠ Con HMAC ✓ Preferido
En la práctica moderna Para la mayoría de casos de uso se prefiere AES-GCM (basado en CTR + autenticación Galois), que proporciona tanto confidencialidad como autenticación en un solo pase. CBC aún se usa pero siempre debe combinarse con un MAC (ej. HMAC-SHA256). ECB nunca debe usarse para datos de más de un bloque.
